# Gateway 本体语义查询总体设计

> 文档状态：方向设计与当前可执行合同
>
> 更新日期：2026-08-11
>
> 适用范围：新 gateway 环境；不依赖旧方案和旧文档即可独立阅读

## 1. 文档目的

本项目希望给云端 Agent 增加企业本体语义能力，使其能够从用户问题出发，找到正确的数据资产和指标，并查询真实指标仓库数据。

当前仓库还保留一组基于 databp、Java resources YAML、逻辑实体遍历和 `locateNode` 的旧设计文档。由于运行环境发生变化，那些文档仅作为历史讨论保留，**不是本设计的实施前提**。新方案不继承旧阶段编号，也不假设旧接口或 YAML 可用。

本文完成三件事：

1. 独立说明新环境、现有工具和严格能力边界；
2. 定义当前立即可落地的“已知叶子节点 ID 后的指标查询”链路；
3. 分析未来业务语言 Grounding 的多种实现路径、步骤、优缺点和推荐组合。

## 2. 参与角色

| 角色 | 职责 |
|---|---|
| 云端 Agent | 理解用户问题、抽取 structuredIntent、调用 MCP 工具、澄清歧义、展示结果 |
| Skill | 约束云端 Agent 的调用顺序、范围、失败策略和禁止事项 |
| Gateway | 暴露 MCP 接口；与其他微服务通过机器接口通信 |
| 弱 Agent | 可读取和修改 Java 仓库中的 gateway；具体编码由专门实施文档指导 |
| 本体及接口维护者 | 维护本体模型和既有接口，完善指标实例信息 |
| 本 Agent | 负责总体语义架构、职责边界、方案比较和实施合同，不代替弱 Agent 猜测 Java 细节 |

## 3. 新环境事实

### 3.1 代码和权限边界

- gateway 与 databp 位于同一代码仓，但属于不同微服务。
- 新能力如果未来需要 Java 接口，应写在 gateway 的 controller 中；微服务之间只允许机器接口通信。
- 当前方案不能调用或复用 databp 进程内的 `treeModelView()`、`locateNode()` 等实现。
- gateway 当前没有获取整棵货架树或全部叶子节点的接口。
- Java resources 中没有可由本项目直接维护的本体 YAML；本项目当前不能直接读取或修改本体定义。
- 本设计的短期目标是不新增接口、不改 Java，优先通过现有工具编排和 Skill 完成闭环。

### 3.2 现有工具

#### getOntologyClassList

返回固定的本体类与关系元数据。目前类包括：

- `Service`：业务服务；查询参数为 code、name；
- `MicroService`：微服务；查询参数为 code、name；
- `AnomalyDetectionTask`：异常检测任务；
- `LogSpace`：日志空间。

关系元数据包括 `associated_with`、`belongs_to`、`contains`、`part_of`。

它不返回类的实例，不返回 `operation_object` 叶子节点目录，也不能把“小艺输入法服务”等名称转换成节点 ID。

#### queryOntologyTopology

从一个已知节点出发查询图结构。

必要入参为：

- `start_node_type`：当前只支持 `operation_object`；
- `start_node_id`：叶子节点 ID；
- `end_node_type`；
- `max_depth`：1-3。

返回 `leftnode`、`rightnode` 和 `edge`。节点信息目前仅保证名称、ID、服务 ID 和 tags；edge type 可能包括 `related_to`、`belongs_to`、`has_member`、`contains`、`part_of`。

图中一个叶子节点下多个逻辑数据实体的指标已经形成指标簇：重复指标被合并，调用方看不到也不需要遍历逻辑实体。

深度合同：

- 深度 1：起始叶子节点的直接指标和直接关系；普通指标问数默认且仅使用这一层。
- 深度 2：还可包含起始节点引用的其他叶子节点及其指标。
- 深度 3：还可包含其他引用中间节点的叶子节点及其指标。

深度 2、3 用于用户明确提出的拓扑、上下游或关联查询，不因深度 1 无结果而自动扩大。

#### queryOntologyInstance

由其他维护者完善中，方向是输入指标 ID，返回指标相关信息。当前暂不作为主链路依赖。需要后续对接的最低元数据合同记录在第 14 节。

#### queryIndicatorDimensionData

成熟的指标数据接口。输入真实指标 ID 和时间段，从指标仓库查询数据。本设计直接使用，不改变其实现。

#### queryKnowledge

与当前指标查询目标无关，从新 Skill 中移除。

## 4. 当前能力判断

### 4.1 已经具备的后半段能力

```text
已知 operation_object 叶子节点 ID
  -> 查询该节点直接关联的真实指标
  -> 在有限真实指标集合内选择目标指标
  -> 按指标 ID 与时间查询真实数据
```

本体图在这里不是普通词典。它表达真实资产、资产关系和指标关系，并将逻辑实体层的重复指标折叠为可查询的指标簇。

### 4.2 尚不具备的前半段能力

```text
“小艺输入法服务”
  -> business_and_platform.CEL.HiInput.service
```

现有工具无法完成这个转换：类列表没有实例，拓扑接口又要求调用前已经知道实例 ID。云端 Agent 不能把猜测的内部 ID 当作企业知识。

因此当前必须区分：

- **Grounding**：业务语言落到真实叶子节点；目前缺失。
- **Graph Orchestration**：从已知叶子节点沿本体图发现指标；目前可用。

### 4.3 当前产品边界

现阶段只实现精确查询，叶子节点 ID 由用户直接提供。业务名称模糊匹配、别名发现、候选学习和确认沉淀在 Grounding 能力落地后再实现。

## 5. 当前已落地：Skill 改造

仓库中的 `skills/metric-query/` 已改为新环境合同，主要变化为：

1. 删除旧 `locateNode -> getNextLevelNode -> resolveMetric` 链路；
2. 禁止访问或遍历逻辑数据实体；
3. 叶子节点 ID 必须由用户直接提供；
4. 普通问数固定 `start_node_type=operation_object`、`end_node_type=indicator`、`max_depth=1`；
5. 从拓扑真实返回中提取指标，按指标 ID 去重并保留关系路径；
6. 只在真实候选集合内匹配指标；多口径时追问；
7. 唯一确定指标后调用 `queryIndicatorDimensionData`；
8. 深度 2、3 只用于用户明确提出的拓扑和上下游查询；
9. 移除 `queryKnowledge` 和每次强制调用 `getOntologyClassList` 的规则；
10. 暂不依赖仍在完善的 `queryOntologyInstance`。

详细执行规范以 Skill 文件为准。

## 6. 当前精确查询闭环

### 6.1 structuredIntent

`structuredIntent` 当前是云 Agent / Skill 的内部工作状态，不要求新增 gateway 接口：

```json
{
  "originalQuery": "查询该节点最近一个月的成功率",
  "operationObjectId": "<用户直接提供的叶子节点ID>",
  "metricPhrase": "成功率",
  "timeRange": {
    "original": "最近一个月",
    "startTime": "<明确时间>",
    "endTime": "<明确时间>",
    "timezone": "<实际时区>"
  },
  "queryMode": "VALUE",
  "maxDepth": 1
}
```

### 6.2 执行链路

```text
用户提供叶子节点 ID
  -> Skill 校验必需槽位
  -> queryOntologyTopology(
       start_node_type=operation_object,
       start_node_id=<用户ID>,
       end_node_type=indicator,
       max_depth=1)
  -> 提取 tags=indicator 的节点
  -> 按指标 ID 去重，保留 edge/path 证据
  -> 在真实候选内匹配 metricPhrase
       -> 唯一：继续
       -> 多个：追问
       -> 没有：如实报告
  -> queryIndicatorDimensionData(metricId, startTime, endTime)
  -> 返回结果、指标身份、时间范围和路径证据
```

### 6.3 安全规则

- 不从业务名称猜 ID。
- 不把“广告推广”扩大成“广告”。
- 不因无结果扩大深度。
- 不把成功率替换成成功次数。
- 不把平均、最小、最大或分位数互相替代。
- 不选择拓扑返回之外的指标。
- 不把图可达解释成指标等价或数值可聚合。
- 空数据保持为空，不用假数据补齐。

## 7. Grounding 的目标模型

Grounding 不只是字符串到 ID 的字典。理想语义链为：

```text
用户表达
  -> 规范业务概念
  -> 业务关系与限定
  -> 承载该概念的 Service / MicroService / operation_object
  -> 经确认的真实叶子节点候选
```

例如“广告推广”不应被声明为“广告”的 alias，而应建模为可能不同的业务概念：

```text
广告推广（BusinessActivity）
  -- implemented_by --> 广告服务（Service）
  -- measured_by ----> 推广成功率（IndicatorConcept）

广告服务（Service）
  -- represented_by -> operation_object 叶子节点
```

这样系统能够解释为什么从一个业务表达走到某个资产，而不是只因字符串相似就扩大范围。

## 8. Grounding 方案一：扩展现有本体与查询能力

### 8.1 核心思路

把业务概念、aliases 以及 Concept 到真实资产的关系作为本体的一部分管理，并让查询接口支持按名称或 alias 检索实例。

不建议把全部信息塞进 `getOntologyClassList`。Class List 的职责应是返回 schema 和可查询参数；实例检索应由单独的通用本体实例查询能力承担。可以扩展 `queryOntologyInstance` 的查询模式，或新增职责清晰的实例搜索接口，具体以本体平台规范为准。

### 8.2 需要建模的内容

- `BusinessConcept`：稳定业务概念；
- `BusinessActivity`：如广告推广；
- `Service` / `MicroService`：已有或待补充实例；
- `OperationObject`：真实叶子资产；
- `IndicatorConcept`：稳定指标口径，可选；
- `alias_of`：表达与规范概念关系；
- `implemented_by`：业务活动由服务实现；
- `represented_by`：业务/服务概念由真实资产承载；
- `measured_by`：业务概念由哪些指标度量。

关系名须由本体治理者最终确定，不能直接把上面的建议名当成既有事实。

### 8.3 查询流程

```text
业务表达
  -> 按 name/alias 搜索 BusinessConcept 或 Service 实例
  -> 沿 represented_by / implemented_by 关系查询 OperationObject
  -> 返回候选 ID、关系路径、置信来源
  -> 唯一且规则允许时锁定；否则用户确认
  -> 进入当前 max_depth=1 指标链路
```

### 8.4 实施步骤

1. 盘点现有本体是否支持新增类、属性、实例和关系。
2. 明确 `operation_object` 为什么未出现在当前 class list，以及是否可注册成正式类型。
3. 定义最小业务概念模型，不先建设大而全本体。
4. 选择少量真实业务表达建立概念、alias、关系和资产映射。
5. 提供按 name/alias 查询实例的机器接口。
6. 返回匹配字段、关系路径和版本，不能只返回一个裸 ID。
7. Skill 仅消费候选并执行确认策略，不在提示词中复制概念库。
8. 建立业务审核、版本、废弃和冲突处理机制。

### 8.5 优缺点

优点：

- 语义、关系、资产映射处于统一治理层；
- 可解释，不只是相似度；
- 可复用于多个 Agent；
- 最符合本体作为企业语义基础设施的目标。

缺点：

- 依赖本体平台和维护者配合；
- 建模与治理成本高；
- 若实例搜索能力缺失，仍需改接口；
- 初期覆盖有限，必须保留未命中和确认状态。

### 8.6 适用判断

如果现有本体允许扩展类、实例、属性、关系与检索，这是长期首选方向。

## 9. Grounding 方案二：Gateway 建立运行时叶子资产目录

### 9.1 核心思路

Gateway 通过机器接口从权威数据源获取全部叶子 `operation_object`，建立只读的运行时资产目录，并提供按名称、alias、路径和服务信息的搜索。

这不是把叶子节点“伪装成本体类”。更准确的定位是：

```text
本体负责关系语义
运行时目录负责当前有哪些真实资产实例
Grounding 负责把业务表达连接到资产候选
```

### 9.2 数据合同

至少需要：

- 稳定叶子节点 ID；
- 中文名、英文名；
- 非空 aliases；
- 完整路径或父级上下文；
- 服务 ID；
- 数据状态和更新时间；
- 是否为可供 `queryOntologyTopology` 使用的 `operation_object`。

字段和来源必须以真实接口为准。

### 9.3 实施方式

优先级从高到低：

1. 调用权威微服务提供的叶子目录机器接口；
2. 若只有分页接口，Gateway 做分页聚合与短期缓存；
3. 若只能获得整树，Gateway 投影为叶子索引，不把整树原样暴露给 Agent；
4. 设置刷新、版本和失效策略；
5. 提供关键词搜索，返回有限候选及路径，而不是把全量目录塞给云 Agent。

Gateway 中若需要示例性接口，方向可以是：

```text
POST /ontology/operation-objects/search
Input:  query, optional serviceId, limit
Output: candidates[id, name, aliases, path, serviceId, matchEvidence]
```

接口名和代码位置均以 gateway 实际规范为准。

### 9.4 它与本体的结合

- 目录搜索负责候选召回；
- `queryOntologyTopology` 验证候选是否是图中的有效起点并发现指标；
- 如果本体后来增加 Concept → Asset 关系，优先使用显式关系；
- 目录名称相似只能构成候选，不能证明业务等价。

### 9.5 优缺点

优点：

- 与实时货架一致；
- 不必手工复制所有叶子 YAML；
- 实现难度通常低于完整本体改造；
- 可为精确名称和已有 alias 提供高质量候选。

缺点：

- 仍主要解决资产发现，不自动理解“广告推广”这样的业务概念；
- 依赖权威目录接口；
- 需要缓存、刷新和权限治理；
- 字符串命中不能代替业务确认。

### 9.6 适用判断

如果本体改造周期长，但能获得权威叶子目录，这是最务实的中短期 Grounding 基础设施。

## 10. Grounding 方案三：关键词 + 向量混合检索

### 10.1 前提

向量检索必须有权威、可刷新、可审计的叶子资产语料。若拿不到全部叶子节点及名称、描述、路径，向量库无从可靠建索引。

### 10.2 索引内容

每个文档对应一个真实叶子资产，包含：

```text
operation_object ID
中文名 / 英文名
aliases
完整路径
服务 ID
业务描述（如果有）
本体中的邻接关系摘要（可选）
数据版本与更新时间
```

### 10.3 检索流程

```text
用户业务表达
  -> 精确 ID / 精确名称 / alias 匹配
  -> 关键词检索（BM25 等）
  -> 向量召回
  -> 规则融合与重排
  -> 用本体约束验证候选类型和关系
  -> 返回 Top-K 候选及证据
  -> 用户确认
```

不要让向量相似度直接决定最终 ID。建议的优先级是：

```text
显式本体映射
> 精确 ID
> 受治理 alias
> 精确名称与路径限定
> 关键词 + 向量候选
```

### 10.4 优缺点

优点：

- 对口语、错别字、长描述和未登记近义表达召回能力强；
- 无需把每种用户说法人工录入 alias；
- 可与关键词检索互补。

缺点：

- 只是候选召回，不是语义裁决；
- 需要同步、索引、Embedding、重排和评测体系；
- 解释性与确定性弱于显式本体关系；
- 数据更新后必须处理索引新鲜度；
- 在资产规模不大时可能明显过度设计。

### 10.5 适用判断

只有在真实资产目录已经可获得、关键词与 alias 召回率被实测证明不足、资产规模和口语变化值得承担复杂度时再引入。

## 11. Grounding 方案四：组合式推荐架构

上述方案不是互斥选项。推荐的长期架构是：

```text
                    ┌─ 显式业务概念 / alias / Concept→Asset 关系
用户业务表达 ─召回─┼─ 运行时叶子资产目录关键词检索
                    └─ 向量检索（必要时）
                              │
                              ▼
                       候选融合与规则排序
                              │
                              ▼
                  本体类型、关系与资产有效性校验
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
             唯一高置信且规则允许      多候选/弱证据
                    │                   │
                    ▼                   ▼
              锁定叶子节点          用户确认
                    └─────────┬─────────┘
                              ▼
                  queryOntologyTopology(depth=1)
                              ▼
                         指标匹配与查数
```

推荐实施顺序不是旧方案的阶段编号，而是按依赖关系推进：

1. 保持当前精确 ID 链路稳定运行；
2. 查清本体平台的实例、alias、关系建模和检索能力；
3. 同时确认权威叶子目录是否能通过机器接口暴露；
4. 优先建立显式本体映射与精确资产搜索；
5. 基于真实未命中语料评估是否需要向量召回；
6. 最后建立用户确认后的知识提案与审核回写。

## 12. 为什么不建议只改 getOntologyClassList

`getOntologyClassList` 当前是 schema 元数据接口。让它直接返回所有实例会混合两个职责：

```text
类和关系有哪些
vs.
当前有哪些真实 operation_object 实例
```

叶子资产量变化后还会引起响应膨胀、分页、缓存和刷新问题。更合理的选择是：

- 可以让 Class List 声明 `OperationObject` 是可查询类型及支持的查询参数；
- 使用实例查询或资产搜索接口返回具体候选；
- 使用拓扑接口查询实例关系。

## 13. 如何处理“广告推广成功率”

### 当前精确阶段

如果用户没有提供叶子 ID：停止并请求 ID。不能执行“广告推广 = 广告”。

### 只有资产目录时

搜索“广告推广”，返回真实名称/alias命中的叶子候选。仅命中“广告”只能作为弱候选，必须确认。

### 本体业务概念完善后

查询“广告推广”业务概念，沿 `implemented_by` / `represented_by` / `measured_by` 等受治理关系得到资产和指标。若概念没有映射，返回知识缺口，不回退为字符串包含关系。

### 混合检索后

向量只补充候选；显式本体映射优先。弱相似候选仍需确认。

## 14. 待对接：queryOntologyInstance 最低合同

这个问题只记录，不阻塞当前精确查询。后续需与接口维护者确认：

| 信息 | 用途 |
|---|---|
| 指标中文名、英文名、描述 | 区分相似指标 |
| 单位、度量类型 | 正确展示和比较 |
| BASIC/DERIVED/COMPOSITE 等类型 | 解释计算属性 |
| GOLD/HEALTH/NORMAL 等级 | 支持指标目录过滤 |
| avg/min/max/P95/P99 等 variant 或口径 | 防止口径替代 |
| 聚合语义 | 防止 Agent 自行错误聚合 |
| 可用维度与过滤参数 | 构造数据查询 |

| 所属服务与来源 | 审计与解释 |

在真实响应合同确认前，这些字段一律视为未知，不得在 Skill 中编造。

## 15. 测试与验收方向

### 15.1 当前 Skill 必测

1. 用户给叶子 ID + 唯一指标 + 时间：深度 1 后查数。
2. 缺少叶子 ID：不调用工具，要求提供 ID。

7. 数据接口空结果：不补零、不换指标。

## 18. 2026-08-11 环境变化：由 ID 起点转向 name 起点

### 18.1 新事实与本文旧合同的关系

`getOntologyClassList` 现在返回更完整的运维资源类型集合，包括 `vm_cluster`、`slb`、`service`、`pod`、`micro_service`、`log_space`、`interface`、`indicator`、`ecs` 等，并返回关系类型元数据。

下一步将扩展 `queryOntologyTopology`，使其能够根据用户提供的运维对象名称查询真实节点 ID，再进入既有拓扑和指标链路。因此，第 4、5、6 节所述“必须由用户直接提供 `operation_object` ID”是上一环境的可执行合同，不再代表下一步目标状态。后半段的真实性约束仍然有效：对象 ID、指标 ID、关系路径和指标数据必须来自真实接口返回，不能由 Agent 编造。

新链路为：

```text
用户表达
  -> 识别任务是否属于运维语义查询
  -> 抽取对象关键词及其本体类型
  -> 在该类型的命名空间内检索真实对象候选
  -> 唯一确定对象 ID，或基于真实候选做最小澄清
  -> queryOntologyTopology 查询真实指标或拓扑
  -> 验证指标口径、维度和查询参数
  -> queryIndicatorDimensionData 查询真实数据
```

### 18.2 本体类型在 name 查询中的作用

name 回查 ID 并不使本体类型失去作用。name 回答“对象叫什么”，本体类型回答“对象是什么”。两者组合形成带命名空间的实体定位，例如：

```text
service::支付
micro_service::支付
log_space::支付
```

只执行 `name LIKE '%支付%'` 可能同时命中服务、微服务、日志空间和指标；加入 `start_node_type=service` 后，可以在服务类型内检索“支付”。它至少提供以下价值：

1. **降低同名误选**：排除其他类型下名称相同或包含相同词的节点。
2. **缩小候选范围**：类型条件能够下推时减少数据库扫描；即使数据库耗时变化不大，也能减少返回条数、Gateway 排序量和 Agent 输入 Token。
3. **支持类型化名称处理**：`pod` 的动态后缀、`interface` 的 URI、`micro_service` 的连字符与版本号可以采用不同归一化策略。
4. **约束查询计划**：起始类型可用于校验合法终点类型和关系，而不只是搜索过滤条件。
5. **提供拒识边界**：无法落到现有类型的无关或未覆盖表达允许返回 `NONE`，不能为满足接口参数强选一个类型。

类型识别应有 `EXACT`、`AMBIGUOUS`、`NONE` 三种结果。显式出现 `SLB`、`Pod`、`ECS` 等类名时可以作为强证据；“服务”“集群”“节点”等泛化词不能单独强制确定唯一类型。高置信类型用于硬过滤，歧义类型只用于候选分组或排序，并触发最小澄清。

### 18.3 本体约束的分层实体解析

下一步不把 name 查询设计成一次无边界的包含匹配，而采用“受控改写、分层召回、应用层排序、真实候选确认”的实体解析流程：

```text
用户对象表达
  -> 分离类型词、对象核心词、环境/地域限定词、状态/动作词
  -> 在本体类型内按层级召回
       1. 原始名称精确匹配
       2. 规范化名称精确匹配
       3. 前缀匹配
       4. 多关键词同时包含
       5. 单关键词包含兜底
  -> 统一计算匹配证据和排序
  -> 唯一强候选则继续；多候选或只有弱证据则澄清
```

以“给我 SLB 集群运行最近 3 天的以主机分组的成功率”为例：

```yaml
subject_type: slb
subject_expression: SLB集群运行
subject_keywords:
  original: SLB集群运行
  core: SLB集群
  type_evidence: SLB
  discarded_as_action: 运行
metric_phrase: 成功率
grouping_dimension: 主机
time_range: 最近3天
```

查询时先保留用户原话，再受控移除明确的状态/动作词，而不是由 LLM 随意生成近义词：

```text
L0: 类型 slb + 名称精确等于“SLB集群运行”
L1: 类型 slb + 规范化名称等于“SLB集群”
L2: 类型 slb + 名称以“SLB集群”开头
L3: 类型 slb + 名称同时包含必要关键词
L4: 类型 slb + 名称包含“SLB”作为弱兜底
```

所以底层可能仍会使用参数化 `LIKE`，但完整能力不等于“执行一个 LIKE”。`LIKE` 只是某些召回层的数据库原语；准确性来自类型约束、查询词规范化、匹配层级、必要关键词组合、候选排序、阈值和拒识。若未来允许调整存储或引入检索设施，可替换召回层为全文索引、拼写纠错或向量召回，而不改变上层实体解析合同。

具体实施行为、分层查询、排序、兼容性和验收要求见 [queryOntologyTopology 按 name 定位节点实施指导](name-query-implementation-guide.md)。

### 18.4 基于角色的多维语义解析

一句用户表达可能同时涉及多个本体概念，但它们在查询中的角色不同。不能把任务简化为“从类列表中选择一个类”。建议的内部语义状态为：

```yaml
task_type: metric_value | metric_trend | indicator_catalog | topology | unrelated
subject:
  ontology_type: slb
  name_expression: SLB集群
target:
  ontology_type: indicator
  metric_phrase: 成功率
dimensions:
  - expression: 主机
    ontology_hint: ecs
    role: group_by
time_range:
  original: 最近3天
```

在示例中，`slb` 是查询主体，`indicator` 是查询目标，“主机”是分组维度。即使“主机”未来映射到 `ecs`，也不能把起始类型从 `slb` 改成 `ecs`。这种角色化解析可以避免多本体词同时出现时的错误竞争，并支持一句话生成完整查询计划。

### 18.5 本体驱动的查询计划

本体识别结果不应停留在一个分类标签，而应形成后续工具可执行的查询计划：

```yaml
query_plan:
  resolve_subject:
    type: slb
    name: SLB集群
  discover_target:
    type: indicator
    phrase: 成功率
    direct_only: true
  validate_dimensions:
    - 主机
  query_data:
    time_range: 最近3天
    group_by: 待真实元数据映射
```

查询计划负责区分起点、终点、关系范围、指标口径、分组维度和时间，但不提前编造真实 ID 或内部参数。计划可以减少 Agent 试错调用、参数错误后的重试和不必要的用户交互。

### 18.6 指标维度和查询参数的语义映射

两篇参考文章中的 Schema 映射和语义查询引擎可转化为本项目的“业务查询表达到真实指标参数”的映射：

```text
“按主机分组”
  -> 规范维度概念
  -> 验证目标指标是否支持该维度
  -> 映射为 queryIndicatorDimensionData 的真实参数
```

理想情况下，指标实例接口返回维度 code、名称、aliases、过滤能力和聚合语义，Agent 只消费真实元数据。当前不能修改本体或数据库时，可以先在 Gateway 的适配层维护有限、可审计的查询参数映射；Skill 负责保留用户原话、要求验证和禁止猜测内部字段。适配层是过渡方案，长期应由权威指标或本体元数据承载。

维度验证必须在查数前完成。目标指标不支持“主机”维度时，不得静默忽略分组、改查 ECS，或返回未分组数据冒充所需结果。

### 18.7 关系感知的受控拓扑查询

关系元数据不只是结果展示文本，还应约束查询路径。对于“服务下的微服务”“接口调用的下游服务”等问题，需要区分 `belongs_to`、`calls`、`related_to`、`similar_to` 等关系的方向、适用类型和可传递性。

在关系合同未确认前：

- `related_to` 不能推导归属、影响传播或数值聚合；
- `similar_to` 不能推导同一对象或指标等价；
- 多跳可达不能自动成为起始对象的直接指标；
- edge description 与 relation type 不一致时不得由 Agent 猜测其真实语义。

当前权限不能修改图和本体时，仍可在 Skill 和 Gateway 中校验查询意图、允许的 edge、方向、深度和结果解释。长期应由本体治理者补充关系的 domain、range、inverse、transitive、symmetric 等机器可执行属性。

### 18.8 当前权限下的优先贡献

当前可修改 Skill 和 Gateway 查询逻辑、不能修改数据库、图实例和本体，因此按以下顺序推进：

1. **本体约束的分层实体解析**：类型内 name 召回、规范化、分层匹配、排序、阈值和拒识。
2. **基于角色的多维语义解析**：区分主体类型、目标类型、指标、维度、时间和关系意图。
3. **本体驱动的查询计划**：用结构化状态减少工具试错和交互轮次。
4. **指标维度及查询参数映射**：优先消费真实元数据，暂缺时建立有限适配层。
5. **关系感知的拓扑约束**：阻止错误方向、错误传递和错误聚合解释。
6. **本体 schema 缓存**：类和关系元数据按版本或短 TTL 缓存，避免每次查询重复获取；未知类型或合同错误时刷新。

超出当前权限但值得保留的演进方向包括：在本体中治理 aliases、业务概念到资产的显式映射、指标维度和查询参数注解，以及关系方向和传递属性。当前不因这些长期能力尚未具备而阻塞代码与 Skill 可完成的小闭环。

### 18.9 建议形成的三个主要贡献点

1. **本体约束的分层实体解析**：将通用 name LIKE 升级为类型约束、受控改写、分层召回、证据排序和拒识组成的真实对象定位能力。
2. **本体驱动的多维查询规划**：将资源主体、指标目标、分组维度、时间和关系意图转为可验证的工具执行计划。
3. **指标语义到真实查询参数的映射**：验证指标支持的维度和聚合语义，再把用户业务表达映射为数据接口参数，避免 Agent 猜测底层字段。

三个贡献共同构成：

```text
用户业务语言
  -> 本体类型与语义角色
  -> 真实运维对象
  -> 受控拓扑与真实指标
  -> 合法维度和查询参数
  -> 真实指标仓库数据
```

本体在其中不是另一个数据库，也不是为接口凑一个必填参数，而是连接用户语言、对象检索、图关系和指标数据的受控语义层。
