# queryOntologyTopology 按 name 定位节点实施指导

> 文档用途：指导实施 Agent 在不了解具体 Java 仓库结构的前提下，实现并验证“按本体类型与对象名称定位真实节点”的能力。
>
> 更新日期：2026-08-11
>
> 边界：本文定义行为、算法和验收合同，不规定 controller、service、repository 的实际类名、注解、包路径或数据库访问规范；实施时服从目标代码仓的既有规范。

## 1. 目标

扩展 `queryOntologyTopology` 的起点解析能力，使调用方可以提供：

```text
start_node_type + start_node_name
```

由 Gateway 定位真实节点 ID，再执行既有拓扑查询。实现必须做到：

1. 类型条件参与查询或候选过滤，不能只查询 name 后忽略类型。
2. 支持用户口语与真实 name 不完全一致的有限模糊匹配。
3. 返回真实候选及匹配证据，不由 Gateway 或 Agent 编造节点。
4. 多候选时不静默选择；无可靠候选时明确未命中。
5. 保留原有按 ID 查询能力，除非现有接口合同明确要求替换。
6. 不修改数据库、图实例或本体内容。

## 2. 先确认现有代码事实

实施 Agent 开始编码前只需要查清与改动直接相关的事实：

- `queryOntologyTopology` 当前请求、响应和校验位置；
- 起始节点 ID 被传给拓扑查询的位置；
- 现有数据访问层能按哪些节点字段查询；
- 节点类型和 name 的真实字段名及大小写规则；
- 现有分页、排序、异常码、日志和测试惯例；
- 按 ID 调用是否已有用户依赖，如何保持兼容；
- 当前查询是否可能跨租户、服务或权限域，已有过滤条件不能丢失。

不要为了套用本文示例而新建与项目风格冲突的抽象。若真实数据合同与本文假设不同，应保留本文的行为目标并按真实结构实现。

## 3. 建议请求语义

逻辑请求至少支持：

```yaml
start_node_type: slb
start_node_name: SLB集群
start_node_id: 可选，兼容旧调用
end_node_type: indicator
edge_type: 可选或依现有合同
max_depth: 1
```

建议的优先规则：

1. 只传 ID：维持旧行为。
2. 只传 name：如果 `start_node_type` 在新合同中必填，返回明确参数错误；不要全类型盲搜。
3. 传 type + name：执行本文的 name 解析。
4. 同时传 ID 和 name：优先按 ID 定位，并校验 name/type 是否一致；具体兼容策略按现有接口规范决定，但不能悄悄使用互相冲突的参数。

`start_node_name` 应是对象表达或由上层提取的核心关键词，不应接收完整自然语言问题。时间、指标和分组维度不属于该字段。

## 4. 核心认识：不是只有一个 LIKE

在不能修改数据库、没有全文检索和 alias 数据的条件下，某些召回步骤最终仍可能用 SQL `LIKE`。这不意味着整个方案只有一次 LIKE。

应将能力拆为四层：

```text
查询词规范化
  -> 分层候选召回
  -> 应用层证据排序
  -> 阈值、歧义与拒识决策
```

`LIKE` 只是“分层候选召回”中的一种底层原语。类型过滤、精确优先、前缀优先、多词约束、排序、候选上限和不确定性处理共同决定最终质量。

## 5. 查询词规范化

### 5.1 保留原始输入

始终保留：

- `original_name`：调用方原样传入；
- `normalized_name`：执行安全、确定性规范化后的名称；
- `tokens`：可用于组合匹配的必要关键词；
- 每一次放宽所采用的规则。

这些信息用于排序、日志、问题定位和最终匹配证据。

### 5.2 只做确定性规范化

可考虑：

- 去除首尾空白；
- 连续空白合并；
- 英文字母大小写归一化；
- 全角、半角的安全归一化；
- 对已确认类型处理 `-`、`_`、空格差异；
- 对 name 字段已有明确规范时采用相同规范。

不得在没有受治理词表时自动扩大近义词，例如：

- “主机”不能自动等价为 `ecs`；
- “广告推广”不能缩成“广告”；
- “负载均衡”不能静默等价为 `slb`；
- “服务”不能自动等价为 `micro_service`。

动作词剥离应优先由上层 Skill 完成。Gateway 如果也实现，只允许维护很小、可审计且不会改变业务实体含义的规则，并保留原始查询作为更高优先级。

### 5.3 类型化规范化是扩展点

如果真实数据证明不同类型存在稳定命名规律，可以逐步增加：

- `pod`：动态 hash 后缀之前的前缀匹配；
- `micro_service`：连字符、下划线、大小写和可识别版本后缀；
- `interface`：URI path、方法名和 HTTP method；
- `ecs`：主机名、资源标识等已存在字段。

没有数据证据时不要先写大量猜测规则。

## 6. 分层候选召回

在 `start_node_type` 范围内按从强到弱的顺序召回。某一强层已经得到唯一可信候选时可以提前结束，避免执行更宽查询。

### 6.1 R0：原始名称精确匹配

```text
type = :type AND name = :originalName
```

这是最高优先级。唯一命中时通常可以直接使用。

### 6.2 R1：规范化名称精确匹配

当数据库或现有查询层支持等价的规范化比较时，比较规范化 name。若不能修改数据库，可在有限候选或既有函数能力范围内处理，不要无界加载某类型的全部节点到内存。

### 6.3 R2：前缀匹配

```text
type = :type AND name LIKE :normalizedName || '%'
```

前缀匹配通常比任意包含具有更强的名称证据，也可能比 `%keyword%` 更容易利用既有索引，实际效果以数据库执行计划为准。

### 6.4 R3：多关键词同时包含

如果输入能安全拆成多个必要关键词，使用 AND 语义：

```text
type = :type
AND name LIKE '%关键词A%'
AND name LIKE '%关键词B%'
```

例如“生产 SLB 集群”在已经确定 `type=slb` 后，可将“生产”和“SLB”作为必要词。不要把中文机械切成单字，也不要把“运行”“查询”等动作词当成必要对象词。

### 6.5 R4：单关键词包含兜底

```text
type = :type AND name LIKE '%' || :coreKeyword || '%'
```

这是弱召回层，必须设置候选上限，不能直接把第一条当作答案。候选排序后仍无明显优势时，应返回多候选或未确定状态。

### 6.6 受治理 alias

只有现有权威数据源已经提供 alias 时才查询。不能由 Gateway 根据模型常识自行生成公共 alias。未来 alias 可作为精确名称之后、普通模糊匹配之前的一层。

## 7. 候选排序

每个候选至少保留以下证据：

```yaml
id: 真实节点ID
name: 真实节点名称
type: 真实节点类型
match_level: exact | normalized_exact | prefix | all_tokens | contains
matched_expression: 使用的查询表达
matched_tokens: 命中的必要词
```

排序建议按稳定规则执行，而不是让 LLM 对大量候选自由判断：

```text
原始精确
> 规范化精确
> 前缀
> 全部必要词命中
> 单词包含
```

同层可再考虑：

- 命中必要词的数量和覆盖率；
- name 与原始表达的长度差；
- 编辑距离或字符相似度；
- 已有 service、tenant、region 等真实限定条件；
- 节点是否满足查询所需的合法类型合同。

字符相似度只能在已经由真实查询召回的小候选集上重排，不能凭相似度创造未返回节点。不要仅因为某候选能够查到数据就替换用户明确指定的对象。

## 8. 唯一、歧义与未命中

建议内部区分：

```text
RESOLVED：唯一强候选
AMBIGUOUS：多个候选，证据不足以唯一选择
NOT_FOUND：没有真实候选
INVALID_INPUT：type/name 不合法或冲突
```

决策原则：

- 原始或规范化精确匹配唯一命中：`RESOLVED`。
- 前缀或包含匹配只有一个候选：可以返回该候选，但携带匹配级别；是否自动锁定由现有产品规则决定。
- 多个候选同层且差异不明显：`AMBIGUOUS`，返回有限候选供上层澄清。
- 只有很弱的包含关系，或关键词过短导致大量结果：不要强选。
- 没有候选：`NOT_FOUND`，不跨类型扩大，不更换用户关键词的业务含义。

如果现有响应合同暂时不能增加状态字段，实施 Agent 应使用项目既有的错误/空结果结构表达相同语义，并在设计说明中记录限制。

## 9. 与拓扑查询的衔接

name 解析得到唯一真实 ID 后，复用既有按 ID 拓扑查询能力：

```text
(type, name)
  -> resolve real node ID
  -> existing topology query(ID, end type, edge, depth)
```

不要复制两套拓扑算法。name 查询新增的是起点解析阶段，而不是改写图遍历语义。

如果解析出多个候选，不应对所有候选静默执行深拓扑查询后拼成一个答案。允许为候选补充少量类型、路径或直接指标证据时，必须设置数量和深度上限，并保持候选身份分离。

## 10. 安全与性能约束

- 所有查询参数必须使用现有安全参数绑定方式，不能拼接 SQL 或查询表达式。
- 对 `%`、`_` 等 LIKE 通配符按既有数据库语义正确转义，避免用户输入改变匹配范围。
- 所有模糊层必须有候选上限和确定排序，避免无界结果。
- 类型、租户、服务、权限和数据状态等既有过滤条件必须在每一召回层保留。
- 强层唯一命中时提前结束；不要固定执行全部层级。
- 记录各层耗时、候选数和最终选择，便于确认优化发生在数据库、Gateway 还是 Agent 环节。
- 不要在一次请求中把某类型全部实例加载给 LLM。

如果当前数据库无法为 `%keyword%` 利用索引，类型过滤、提前结束和候选上限仍能改善端到端成本；但不能宣称数据库查询必然更快。应以执行计划和压测为准。

## 11. 与 Skill 的职责边界

Skill 负责：

- 判断是否为运维语义查询；
- 从完整问题中抽取主体类型、对象表达、指标、维度和时间；
- 类型无法确定时输出 `NONE` 或做最小澄清；
- 不把完整问题直接塞进 `start_node_name`；
- 消费真实候选，不编造 ID；
- 多候选时向用户展示最少必要差异。

Gateway 负责：

- 校验 type/name；
- 在真实数据内执行分层召回；
- 规范化和稳定排序；
- 返回真实 ID、name、type 和匹配证据；
- 唯一命中后复用既有拓扑查询；
- 执行安全、权限、分页和候选上限。

不要让 Skill 维护企业实例名称或 ID，也不要让 Gateway 负责理解完整自然语言问题。

## 12. 必测场景

### 12.1 精确命中

同一 type 下 name 完全相等，返回唯一真实 ID，并进入既有拓扑查询。

### 12.2 类型隔离

`service`、`micro_service`、`log_space` 下存在同名“支付”，传 `type=service` 时只能返回 service 候选。

### 12.3 规范化命中

验证大小写、首尾空格及已支持符号差异不会导致错误未命中，同时响应保留真实 name。

### 12.4 前缀优于包含

候选包括“支付服务”和“新支付服务平台”时，查询“支付”应使前缀候选排在普通包含候选之前。

### 12.5 多关键词约束

查询“生产 支付”时，优先返回同时含两个必要词的候选，不因只含“支付”而提前锁定。

### 12.6 多候选不静默选择

同层存在多个近似候选时返回 `AMBIGUOUS` 或等价的既有响应，而不是使用数据库第一条。

### 12.7 未命中不跨类型扩大

`type=slb` 下没有候选时，不自动到 `elb_loadbalancers`、`service` 或全类型搜索。

### 12.8 特殊字符安全

name 包含 `%`、`_`、引号、反斜杠等字符时不扩大匹配、不报未处理异常、无注入风险。

### 12.9 兼容按 ID 查询

旧请求只传 ID 时行为和结果不变。

### 12.10 性能与上限

验证强层唯一命中不会继续执行弱层；宽泛关键词只返回受限候选；记录各层候选数量与耗时。

## 13. 验收指标

使用一组包含精确名称、口语名称、同名跨类型、多候选、无关词和未命中的真实样例，对比改造前后的：

- Top-1 对象命中率；
- Top-K 召回率；
- 错类型命中率；
- 平均候选数；
- `AMBIGUOUS` 与 `NOT_FOUND` 的正确率；
- name 解析 P50/P95 耗时；
- 整条 Agent 链路的工具调用数和澄清轮次；
- 按 ID 旧链路回归结果。

成功标准不能只写“支持 LIKE 查询”。至少应证明类型约束和分层策略相较于无类型的单次 `%keyword%`：

- 不降低真实对象召回率；
- 显著降低错类型候选和平均候选数；
- 不增加无界查询；
- 在模糊场景下返回可解释候选而不是静默误选。

## 14. 实施输出要求

实施 Agent 完成后应报告：

1. 修改了哪些与该接口直接相关的文件；
2. 最终请求与响应合同；
3. 实际采用了哪些规范化和召回层；
4. 如何保留按 ID 兼容性；
5. 如何表达唯一、多候选和未命中；
6. 安全、候选上限和权限过滤如何保证；
7. 执行了哪些单元、集成和回归测试；
8. 哪些能力因现有数据层限制未实现，例如全文检索、alias 或拼写纠错。
